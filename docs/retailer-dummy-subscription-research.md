# Retailer dummy subscription research

Research date: 2026-09-08. Repository source inspection only; no application, schema, seed, database, or commit changes. Citations below identify inspected repository files and line numbers. No live database contents or deployed behavior were verified. All design choices in the proposal sections are recommendations, not existing behavior or approved commercial policy.

The product requirements come from the user's subscription request and supplied profile reference image (`codex-clipboard-5faf609f-585c-4d9d-a332-cc3d1cbf5aff.png`). The image supplies the seven User Plan labels; the latest request supplies the View Subscription modal and dummy-payment flow.

## Recommendation and scope

Add a dedicated retailer subscription catalog, durable dummy purchases, and persisted subscription terms. Admins manage seeded **Free, Monthly, Six-monthly, Yearly** plans in an explicit **Retailer Subscriptions** tab/subsection of Packages. The retailer profile opens **View Subscription**, showing the current term and eligible admin-configured options. Confirming a server quote records a dummy payment and atomically activates a real persisted term.

Two product decisions need particular attention: recommend **non-expiring Free**, although existing `free_trial` copy says 14 days; recommend **immediate upgrades to longer paid terms with no proration**, which forfeits unused time and credit. Neither recommendation is approved policy. The confirmation must disclose the latter before activation.

Scope excludes real payment gateways, automatic recurring charges, feature/access gating, invoices, accounting, referral changes, and warehouse subscriptions. Auto Renewal remains **Off** and Next Billing Date **Not scheduled**; expiry is a separate date.

## Proposed schema and catalog

Use three dedicated tables; proposed names/fields below are not existing schema. Preserve `selectedPlan` as legacy registration metadata.

| Table | Minimum durable data and invariants |
| --- | --- |
| `retailer_subscription_plan` | ID; unique immutable code (seed codes `free/monthly/six_monthly/yearly`); editable name/description; supported duration `null/1/6/12` months; total `amountMinor` as integer poisha; currency BDT; active flag; display order; version; created/updated timestamps and admin actor. Free is zero; paid totals positive. No destructive deletion of referenced or seeded plans. |
| `retailer_subscription_purchase` | UUID, owner/shop FK, plan FK, provider fixed to `dummy`; quote state `pending/confirmed/expired`; immutable plan code/name/version/duration/total/currency snapshots; prior current-term ID/version; server quote expiry; confirmed time; unique `(shopId, idempotencyKey)` plus request fingerprint; activated term ID/result. A pending row is the durable server quote; confirmation marks simulated payment successful. No card, bank, or mobile-wallet details. |
| `retailer_subscription` | UUID, shop FK to owner user; plan FK; nullable unique purchase FK (Free provisioning has no purchase); immutable bought-term snapshots; server `startsAt`, nullable `expiresAt`; lifecycle `active/superseded`; `isCurrent`; `supersededAt`; version; provision source such as `approval/backfill/dummy_purchase`; `autoRenew=false`, `nextBillingAt=null`. Partial unique index on `shopId WHERE isCurrent` gives at most one current term; provisioning/confirmation ensures one for each eligible initialized retailer. |

Require same-shop linkage between purchase and term through composite constraints or equivalent transactional enforcement. Paid terms require a confirmed purchase, positive duration/amount and `expiresAt > startsAt`; Free requires zero amount and null expiry. Keep previous terms and purchases for history. Catalog edits/deactivation affect future purchases, never existing snapshots, dates or payment outcomes. UI reads bought names/prices from snapshots, not a mutable catalog join. A current term can be expired: “current” means the selected/latest term, not proof it remains active.

Seed the four initial plans and let admins create, edit and deactivate paid catalog entries within the supported 1/6/12-month durations. Recommend one active option per paid duration, enforced by a database constraint, so replacing a plan means retiring the old offer and activating its replacement. Admin-created plans get their own immutable codes; existing purchases retain their snapshots. Free remains available as the provisioning default. Duration, rather than name or display order, determines upgrade eligibility. Additional durations or feature tiers remain outside this MVP.

Illustrative BDT amounts only — **not approved pricing or authorization to seed these amounts**:

| Plan | Term | Total due once | Effective monthly cost |
| --- | --- | ---: | ---: |
| Free | No expiry, proposed | ৳0 | ৳0 |
| Monthly | 1 calendar month | ৳1,000 | ৳1,000 |
| Six-monthly | 6 calendar months | ৳4,800 | ৳800 |
| Yearly | 12 calendar months | ৳7,200 | ৳600 |

The requirement concerns **effective monthly price**, not total fee: `Monthly > Six-monthly/6 > Yearly/12`. Validate active offers on the server, using integer comparisons (`6*M > S`, `2*S > Y`) and bounded safe integer amounts; compare the durations still offered when an option is inactive. Serialize catalog creation, edits and activation using one stable catalog lock, so concurrent inserts/edits cannot violate this cross-row invariant. Display both total due and effective monthly cost; never imply a yearly purchase costs less in total than one month.

## Proposed API and secure confirmation

Register dedicated routers beside existing routers. Keep `adminLanding` and public landing pricing intact. Proposed endpoints:

| Operation | Access and contract |
| --- | --- |
| Admin list/create/update/activate retailer plans | `adminProcedure`; explicit retailer subscription namespace. Validate supported durations, unique codes, active price ordering, immutable purchased-term definitions, version conflicts and archival restrictions. No admin “mark paid” shortcut is needed. |
| GET current subscription and available options | Owner only initially; returns all seven display facts, current snapshot, server-computed effective status, server time, plan versions, eligible actions/reasons. Optional staff read requires an explicit read permission and server-resolved shop scope. |
| POST quote `{planId}` | Owner only; create pending durable purchase with amount/duration/name snapshots, current-term version and short server expiry (suggest 10 minutes). Return total/currency, duration, upgrade/no-credit disclosure and date preview. Client supplies no authoritative amount or dates. |
| POST confirm `{quoteId, idempotencyKey, acceptDummyPayment: true}` | Owner only; verify and consume the quote once, persist dummy payment success and activate the term in one transaction. Return purchase and subscription results for cache refresh. |

Eligibility is checked against fresh server records at quote and confirmation: exact owner, `businessType=retail`, approved seller status, no current ban/disabled state, and a valid owner-linked approved application for the normal registration path. Do not use phone fallback, request `shopId`, arbitrary user IDs, `isSeller` alone, or UI visibility as authorization. Legacy owners lacking an approved application need explicit backfill review. Staff, warehouse owners, restaurants, consumers and admins using the retailer purchase endpoint are rejected by default; admins only manage the catalog. Eligibility here authorizes purchase and does not gate ordinary product features.

Confirmation transaction:

1. Lock the owner row as the stable per-shop serialization point (also works when no subscription exists). All provisioning/confirmation writers use this lock. Revalidate eligibility; fetch the quote only within this shop.
2. Resolve retries: a matching previously confirmed key/quote returns the saved purchase/activation result without changing dates. Reusing a key with different quote/payload conflicts. A consumed quote cannot activate another term even with a new key. Resolve committed retries before rejecting an elapsed quote expiry or a now-inactive plan.
3. Lock/reload the selected plan and quote; reject unconfirmed expired quotes, inactive plans, changed plan versions, or changed prior-term ID/version. Return a re-quote conflict so the owner sees new terms; never silently accept a different price. Check effective expiry again and re-evaluate the allowed action.
4. Calculate amount from the validated server quote/catalog, duration from the server snapshot, and actual activation time from one server clock instant. Compute expiry using the calendar rule below. Never trust the client clock or client-calculated total. Quote date previews are estimates until confirmation.
5. Supersede the previous current term, insert the new current term with snapshots, bind the confirmed dummy purchase and idempotency result, and commit. Unique current-term/purchase/key constraints defend against races; recover a uniqueness conflict by reading the matching result, or return conflict for a different request. A failure rolls all activation/payment changes back.

Concurrent tabs with different quotes must not each buy/replace a term: their prior-term version binds each quote to the state the owner reviewed. A lost response is retried with the same key. A canceled dialog or abandoned quote leaves the existing subscription unchanged. A later failed attempt does not change an already bought term's Payment Status.

Remove the old registration-plan editor from User Plan. Retire its plan-changing route if unused, or retain it solely as explicitly labeled registration metadata; it must never activate, replace or price a subscription. All paid activation uses confirmation. Reuse the existing dialog/query patterns, but invalidate current subscription, eligible options and shop summary after success and confirm persistence by refetch/reload.

## Proposed exact field display and lifecycle

Keep the **User Plan** section and all seven labels exactly. Replace the reference's old **Update User** button with the latest requested **View Subscription** action. Show current details first, followed by admin-configured upgrade cards and a dummy-payment confirmation step with a clear “no money will be charged” message. Do not supply hardcoded fallback purchase plans when catalog loading fails.

| Exact field label | Free default proposal | Paid term proposal |
| --- | --- | --- |
| Current Plan | Free snapshot name | Bought plan snapshot name |
| Subscription Status | Active | Active while `startsAt <= now < expiresAt`; Expired at/after expiry |
| Plan Start Date | Actual Free provisioning date | Actual successful activation date |
| Expiry Date | No expiry | Activation plus 1, 6 or 12 calendar months |
| Auto Renewal | Off | Off |
| Next Billing Date | Not scheduled | Not scheduled |
| Payment Status | Not required | Paid (Dummy), including after term expiry |

Persist timestamps as timezone-aware instants. Proposed business rule: add calendar months in **Asia/Dhaka**, preserve local time, clamp the day to the destination month's last valid day, then store the resulting instant. Compute directly from activation plus the full duration, not repeated one-month additions. For example, Jan 31 plus one month ends Feb 28/29; leap-day plus twelve months ends Feb 28 next year. Treat expiry as exclusive and format dates consistently in Asia/Dhaka; show the exact expiry time in confirmation/details when needed.

Derive expiry status on each read and purchase eligibility check; no cron or GET-side database write is necessary. Persist lifecycle transitions and term dates; return the time-derived effective status consistently to profile, modal and dashboard. Keep an expired paid term current until a new purchase so history/payment facts remain visible. Do not automatically replace it with Free, schedule a renewal or block access. Missing/uninitialized records show unavailable state with a recovery path, never fabricated active or paid values.

Recommended purchase rules, subject to product decision:

- Free → any active paid plan: activate immediately.
- Active Monthly → Six-monthly/Yearly; active Six-monthly → Yearly: activate immediately, replace the old term, charge the full dummy total, **no proration/refund/credit/carryover**. Confirmation explicitly states unused term and credit are forfeited and displays the old expiry/new term. Preserve both purchases/terms.
- Active same-plan repurchase and active shorter-term/Free downgrade: disallow for MVP; avoid resetting an existing term accidentally. Yearly has no longer-term upgrade.
- Expired paid term → any active paid plan, including the same plan: allow manual renewal/restart from confirmation time. No backdating or early renewal stacking. Selecting Free after paid expiry remains a separate open policy decision.

The shop banner should consume the same subscription DTO and open View Subscription. For the admin dashboard, either split authoritative retailer counts from clearly labeled warehouse legacy estimates, or explicitly scope a new KPI to retailers. **Do not replace the combined KPI with retailer-only data while labeling it all subscriptions.** Deduplicate retailer counts by shop, derive expiry identically, and treat “expiring soon” as an overlapping subset of active paid terms or document another consistent counting convention. This does not introduce warehouse subscriptions.

## Proposed migration, seed and backfill sequence

1. Recheck the latest migration journal and duplicate marketing declarations; add reviewed additive SQL, Drizzle definitions/relations/indexes and journal metadata following current repository conventions. Inspect generated changes for unexpected drops or snapshot drift. Do not run `db:push` as a substitute for reviewed migration history.
2. Add a dedicated explicit subscription seed command with stable unique codes and approved/configured prices. Run inserts in a transaction with conflict-do-nothing on code; validate the resulting catalog. Report created/existing/conflicting rows. Re-running must preserve admin prices, names, versions and inactive flags. Do not copy accounting seed's overwrite behavior or create plans on ordinary GET requests.
3. For new retailer approvals, add Free initialization inside the same transaction as core application/user approval writes, using the owner lock and conditional pending-status transition. Make the provisioning helper retry-safe; no second Free term if one already exists. Existing referral/KYC side effects are a separate concern: preserve behavior, do not replay them to provision subscriptions, and do not broaden this into a referral redesign.
4. Backfill only eligible approved retail owners with no subscription, one per owner, under the same lock/unique invariant. Use the actual backfill time as Free start and mark source `backfill`; do not pretend it began at historic registration. Preserve legacy selectedPlan values. Neither Starter/Growth selection nor the dashboard heuristic proves payment, so do not manufacture paid terms or migrate marketing tier prices automatically. Report missing owner/application links, mismatched approval states, duplicate/ambiguous applications and unknown preferences for review; never merge identities by phone.
5. Make backfill rerunnable with dry-run counts and created/skipped/anomaly totals. Skip existing paid/current terms and exclude staff, restaurant/warehouse users, pending/rejected/disabled/banned owners by default. Check eligible-owner coverage, one current term each, and zero synthetic paid purchases. Legacy excluded accounts need a deliberate resolution, not silent paid/Free defaults.
6. After migration/seed/backfill verification, switch retailer profile/banner to the new reads and update admin KPI labels/scope together. Keep onboarding selection informational until its copy is deliberately aligned; do not continue presenting a 14-day trial as the new Free policy. Rollback should preserve purchase/history tables and disable affected entry points instead of deleting subscription data.

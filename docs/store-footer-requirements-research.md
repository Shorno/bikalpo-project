# Store footer requirements: existing capabilities and gaps

Date: 2026-09-05. Scope: read-only source inventory against the supplied **BIKALPO — SELLER STORE VIEW / Header Navigation, Content & Page Connection Specification**, sections 1–21. The client document is requirements/reference material, not authorization to implement its missing systems. This note adds no application features. No database contents, credentials, or production behavior were inspected; “exists” means supported by checked-in source, not live verification.

## Main finding

The retailer store has real identity/contact/header/catalog data and reusable account workflows. Its footer is currently platform-oriented and receives no store data. Most requested support and policy labels are **not ready-made store-specific destinations**: tickets, order complaints, tracking, and item requests exist with narrower or different scope. Terms, Help Center, and Contact have routes but explicitly provisional content. Real store policies, automatic store-context support/messaging, verified store reviews, and configured app downloads are gaps rather than simple footer links. Sources are linked below.

Status meanings: **Existing** = implemented capability matching that specific observation; **Partial** = useful implementation exists but the client requirement is not met; **Missing** = no matching public surface/model was found in the inspected routes, components, API and schema searches. An existing backend is not evidence of a connected footer action.

## Intended ownership and navigation

The document requires one common footer design with store-specific About/Product/Brand/Review anchors, store social channels and contact details, and store identity in copyright. Report Issue concerns the chosen store; Request Item must preserve its store association and seller messaging must target that seller. Return/refund, delivery and cancellation content must clarify store versus platform policy. App downloads, Terms, Home, All Stores, Help Center and platform Contact belong to Bikalpo. Example names, ratings, phone numbers, `support@bikalpo.com`, hours such as `24/7`, and sample URLs are illustrative, not store facts. The header illustration is context for the footer's About Store target, not a separate header-redesign scope.

The document suggests the detailed report-context fields, guest tracking, and ideally CMS/database-managed policy content; these are not all mandatory implementation requirements. Their absence is recorded to explain current capability, not expand this footer task. Global app configuration is the document's proposed source for platform download links.

Because the footer is mounted in the store layout, it also appears under product detail routes. Future anchor wiring would need the store root path, e.g. `/stores/{slug}#store-products`, when used outside the store landing page. The existing layout passes `slug` to the header but calls `<ShopFooter />` without props. [Store layout](../apps/web/app/(retailer-storefront)/stores/[slug]/layout.tsx#L5)

## Important workflow distinctions

### Report a store versus report an order

The actual `/account/support` page renders `UserSupportPanel` as a consumer. The panel loads shops from order history, requires a manual selection and submits `shopId`. The API validates a shop owner user and initially assigns the ticket to that user; it does not accept a store name/current URL nor prefill from query parameters. Ticket records contain creator and assignee identities, replies and escalation information. The unrelated `support-client.tsx` file with FAQ tabs is not what this route mounts. [Support route](../apps/web/app/(public)/account/support/page.tsx#L3), [selection/submission](../apps/web/components/support/user-support-panel.tsx#L150), [shop options query](../packages/api/src/routers/user-ticket.ts#L743), [ticket model](../packages/db/src/schema/support.ts)

Order detail has a working report dialog calling `userComplaint.create`. That endpoint requires an owned order, rejects pending/cancelled orders, prevents duplicate active complaints and sends complaints to the admin pool. `/account/complaints` lists these complaints. This is useful existing behavior, but does not meet an arbitrary store complaint initiated directly from a public footer. [Order report action](../apps/web/components/shop/order-detail-client.tsx#L112), [complaint endpoint](../packages/api/src/routers/user-complaint.ts#L53), [complaint list](../apps/web/app/(public)/account/complaints/page.tsx#L128)

The “Chat Store” and “Report Issue” buttons in `/shop/dashboard/stores` are explicitly disabled. They are in management UI and are not evidence that public seller chat/report routing exists. [Disabled buttons](../apps/web/app/shop/(management)/dashboard/stores/page.tsx#L400)

### Account tracking and item requests

The public account layout redirects guests to `/login?redirect=/account`; the account-named routes are not anonymous lookup pages. The tracking API chooses the newest non-open, non-delivered/cancelled/returned order for the authenticated user. Both `/account/track` and `/shop/account/track` render the same component, which navigates to `/account/orders...`. [Account layout](../apps/web/app/(public)/account/layout.tsx#L13), [tracking API](../packages/api/src/routers/customer.ts#L2653), [shop track route](../apps/web/app/shop/(storefront)/account/track/page.tsx#L1)

`/account/requests` and `/shop/account/requests` provide request lists; `RequestFormModal` submits item name, brand, category, quantity, description and image. The persistence model records customer identity and admin processing metadata, not a shop association. Admin approve/reject/suggest workflows are present. Merely linking this interface cannot turn it into a store-specific request. [Request page](../apps/web/app/(public)/account/requests/page.tsx#L7), [form submission](../apps/web/components/features/item-request/request-form-modal.tsx#L105), [request model](../packages/db/src/schema/item-request.ts#L23), [admin processing](../packages/api/src/routers/admin-item-request.ts#L172)

### Store review provenance

Existing rating data is not necessarily fake: it comes from product review records. The catalog itself selects this shop's own products, so this finding does not establish leakage of other stores' shared-product ratings. However, the current store aggregation follows product IDs in that catalog and does not apply a verified-purchase predicate. Review creation permits reviews without a purchase and determines `isVerifiedPurchase` from a matching product order, without recording explicit shop-specific review attribution or requiring verified delivery. It therefore does not provide the requested dedicated verified store review section. [Store aggregation](../packages/api/src/routers/customer.ts#L4172), [review creation](../packages/api/src/routers/customer.ts#L5974), [review schema](../packages/db/src/schema/review.ts#L17)

## Boundary for a footer-only follow-up

Existing identity, phone, real hours, store URL, header/catalog targets, dynamic year and known platform/account routes offer a limited wiring/composition path. Existing workflows must keep accurate labels and scope. Linking a global item request, order complaint, or manual shop ticket cannot be reported as satisfying the store-context requirement.

The missing brand/review sections, direct messaging, contextual store reports, store-bound item requests, store policy publication/CMS, guest tracking, new social fields and app configuration are separate product/data work. The current request authorizes inventory only; none were implemented. Before any implementation claim, distinguish working existing destinations from provisional pages and unavailable actions. The supplied document's sample policy wording and example values must not become published facts through a visual footer change.

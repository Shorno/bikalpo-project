# Product identity, inventory, and transaction storage audit

Date: 2026-09-28. Baseline: `51f05a07e9025d55e250b25d089cdbd3e7e4c1b4`.

Scope: repository source inspection for the proposed Product System ID, Inventory ID, and readable SKU. No database mutations, application changes, or live data claims are made in this note. The requirements and recommendations below are distinct from current behavior.

## Client requirement interpreted in English

The supplied example calls for a system-generated, permanent Product System ID such as `SYS-000000000001`; the product's Type must never change after creation. An Inventory ID such as `INV-030000000001` identifies one exact stockable variant, including relevant attributes such as color and size. A readable SKU such as `APX-SHOE-BLK-42` is visible to visitors, customers, retailers, wholesalers, sales staff, and warehouse staff and is usable in search, sales, and purchasing.

The example establishes that Black/40, Black/41, Black/42, and White/40 must have distinct identities and separate stock. It does not establish what `03` means, whether a System ID denotes a generic core or a branded product, or whether equivalent goods at two owners share an Inventory ID. Those are domain decisions, not details that can safely be inferred from padding an existing number.

## Existing generation, aliases, and safeguards

The canonical rollout in migration 0037 creates one sequence-issued BKV identity per core/brand/option, links compatible existing owner variants, backfills canonical order references and SKU snapshots, and adds an active product/canonical-variant unique index. It keeps integer foreign keys rather than using display SKUs as keys. The migration infers one conversion target only when the existing source has a single distinct canonical target. [Migration and backfill](../../packages/db/src/migrations/0037_global_catalog_variant_foundation.sql#L3), [conversion backfill](../../packages/db/src/migrations/0037_global_catalog_variant_foundation.sql#L90), [order snapshots](../../packages/db/src/migrations/0037_global_catalog_variant_foundation.sql#L112)

The generated-variant synchronizer issues local `CP-{productId}-B{brandId}-VO-{optionId}` SKUs. It links missing canonical identities with insert-on-conflict followed by exact identity lookup, and deactivates/reuses removed options rather than deleting their rows. The buyer-target helper separately uses transaction advisory locks to coordinate canonical and owner-specific creation. [Generated rows](../../packages/api/src/routers/helpers/sync-generated-variants.ts#L207), [canonical linking](../../packages/api/src/routers/helpers/sync-generated-variants.ts#L132), [deactivate/reactivate contract](../../packages/api/src/routers/helpers/sync-generated-variants.ts#L247), [buyer identity lock](../../packages/api/src/routers/helpers/b2b-buyer-target.ts#L33)

Several different things are currently called SKU:

- A hierarchical helper composes Type/Category/Subcategory/Core/Brand/Variant Option codes into 15 digits. Its scoped allocation uses `MAX(code) + 1`; it is not a suitable new concurrent global identity allocator. [Generator](../../packages/api/src/routers/helpers/generate-sku.ts#L1), [allocation](../../packages/api/src/routers/helpers/generate-sku.ts#L37)
- Owner configuration also generates `SHOP-...` and `WH-...` local SKUs. Product-level versions can contain a shortened owner ID; these strings must not be treated as authoritative global uniqueness. [Shop product and variant creation](../../packages/api/src/routers/helpers/b2b-buyer-target.ts#L253), [warehouse generation](../../packages/api/src/routers/helpers/b2b-buyer-target.ts#L477)
- `preferred_local_sku` and `classification_code` are nullable rollout fields. Source searches found schema declarations and readers but no application issuance/update path for either field at this baseline. `sku` and `preferred_local_sku` have no unique constraint in the Owner Variant schema. [Variant fields](../../packages/db/src/schema/product-variant.ts#L78), [preferred alias](../../packages/db/src/schema/product-variant.ts#L230), [classification code](../../packages/db/src/schema/catalog-variant.ts#L45)
- `warehouse_variant_alias` is a display label per warehouse/core/option, not a SKU alias registry, and its scope does not include brand or color. [Alias table](../../packages/db/src/schema/warehouse-variant-alias.ts#L14)

Migration 0038 prevents shop and warehouse inventory from pointing to another owner's variant. It also requires structured B2B lines to retain the source canonical identity and permits only the same canonical variant or the configured canonical conversion target. Legacy unstructured lines explicitly bypass the latter guard. These boundaries must survive any ID redesign. ## Main gaps against the client example

1. **Color × size is not a complete canonical identity today.** Color and size are free-text Owner Variant fields. Canonical uniqueness uses only core + brand + option, and the structured `attribute` option contains one attribute/value pair. Generated admin variant rows do not populate color or size; owner configuration can copy an option's size but has no normalized multi-attribute combination key. The same brand/option with Black and White cannot safely represent two independent canonical items. The active `(product_id, catalog_variant_id)` unique index would reject two such owner rows linked to the same canonical identity; this is a design incompatibility, not evidence that current stock has already been merged. Across different owners, color-blind canonical linking could still equate different physical combinations because the unique index is product-scoped. [Active variant constraint](../../packages/db/src/migrations/0037_global_catalog_variant_foundation.sql#L112) Add normalized product attributes and an exact combination signature or equivalent relational uniqueness, and include every identity-bearing axis in canonical selection, prices, synchronization, and matching. [Attributes](../../packages/db/src/schema/product-variant.ts#L126), [definition](../../packages/db/src/variant-definition.ts#L19), [canonical key](../../packages/db/src/schema/catalog-variant.ts#L68), [generated variant](../../packages/api/src/routers/helpers/sync-generated-variants.ts#L221)
2. **Readable SKU issuance and uniqueness are not implemented as the client describes.** Neither `CP-...` nor BKV is the proposed mnemonic SKU. `APX-SHOE-BLK-42` may collide across two shoe models from the same brand. A model/product token or deterministic collision suffix is necessary; uniqueness must be enforced in the selected global or owner scope, not just checked in the UI. Preserve historical aliases when a readable SKU is changed. The required alias registry and collision policy are proposals. [Current generation](../../packages/api/src/routers/helpers/sync-generated-variants.ts#L226), [current unconstrained local SKU](../../packages/db/src/schema/product-variant.ts#L78)
3. **Type permanence needs explicit enforcement.** The core stores category/subcategory, with Type reached through the category. The core update currently spreads editable identity fields into the update, without a Type immutability comparison in that handler. The new rule must also cover moving the category to another Type and reassigning a core/product to a category under a different Type. Persist an immutable Type reference on the entity receiving SYS and enforce consistent category membership in server and database constraints/triggers. [Core hierarchy](../../packages/db/src/schema/core-product.ts#L61), [Type query traversal](../../packages/api/src/routers/admin-core-product.ts#L77), [core update](../../packages/api/src/routers/admin-core-product.ts#L436)
4. **Canonical linkage is not a general identity-change guard.** The linker skips already-linked rows; the buyer helper returns an existing canonical row without comparing the whole current definition. Therefore changing owner/core/brand/attributes must be prohibited or explicitly migrated before relying on those helpers for the new contract. Used Variant Options already have a useful structure/scope lock, with an explicit legacy-upgrade exception. [Link skip](../../packages/api/src/routers/helpers/sync-generated-variants.ts#L147), [existing canonical lookup](../../packages/api/src/routers/helpers/b2b-buyer-target.ts#L94), [used option lock](../../packages/api/src/routers/admin-variant-option.ts#L266)

## SYS and INV placement alternatives

These are proposed interpretations, not changes already agreed with the client.

| SYS placement | Meaning | Consequence |
|---|---|---|
| Existing `core_product_identity` | One System ID for generic Sports Shoe across brands and owners. | Smallest root-identity change, but SYS alone does not identify one actual branded product. Explicitly label it a core/root ID. |
| Existing `product` | One permanent ID for each actual database Brand Product. | Directly identifies today's product record, but equivalent goods at admin, warehouse, and shop have different SYS codes. |
| New shared branded-product entity | One System ID for a canonical core + brand/model product; owner `product` rows reference it. | Recommended if the client expects the same actual product to have one platform identity across owners. This is a deliberate domain extension; Core Product Identity remains reusable setup. |

For a platform-wide interpretation, make `INV-` the business code of the expanded **Catalog Variant**, replacing BKV as the primary displayed code while keeping old BKV values resolvable. Keep Owner Variants and owner stock balances separate. A warehouse and retailer holding the identical Black/40 item then share SYS/INV/readable global SKU but have different owner-variant and balance keys and independent quantities.

If the client instead means a distinct stock-record ID for every owner, place INV on the owner inventory record and retain a separate canonical variant key for matching and transfers. Never use an owner-specific INV as though it were the cross-owner product identity. The supplied document does not resolve this distinction; the requirements must state the selected interpretation explicitly.

The initial `03` in `INV-030000000001` must not be assigned to a guessed Type. If confirmed as a two-digit Type code, freeze it at issuance and allocate the remaining ten digits atomically within the defined namespace; never renumber when category labels change. Otherwise use a twelve-digit opaque sequence. Both SYS and INV examples require 16-character strings including their prefixes, not numeric API values.

## Recommended migration and acceptance boundaries

1. Settle and record SYS entity, INV scope, brand/model uniqueness, the meaning of `03`, and whether owners can choose local SKU aliases. These decisions shape the schema and must precede code issuance.
2. Keep integer relational keys. Add database-issued, non-null, unique, immutable business-code columns on the selected entities. Use bounded sequences or locked counter rows with explicit overflow handling, never row counts, `MAX + 1`, padded truncation, or shortened UUID/user-ID fragments. Codes are never recycled; gaps are acceptable.
3. Introduce exact canonical attribute combinations first. Migrate only unambiguous rows; report and manually resolve missing core/brand/option, duplicate owner variants, conflicting colors/sizes, and canonical links inconsistent with their definitions. A new display ID cannot repair incorrect underlying identity.
4. Backfill codes deterministically without changing stock quantities, local variant PKs, order associations, conversion targets, prices, or historical snapshots. Preserve BKV and legacy SKU resolution in an explicit alias mapping. Existing ambiguous aliases must return a disambiguation result, not silently choose the first match.
5. Migrate all creation paths, including admin generation, owner configuration, and automatic buyer-target creation. Centralize issuance/resolution, API field names, UI labels, printed documents, and scan/search behavior.
6. Add database and application enforcement for Type permanence and immutable canonical identity. Archive or replace a structurally different product/variant; do not mutate the identity of historically transacted goods.
7. Acceptance tests must prove: the client's four shoe combinations have distinct INV/SKU values and stock; identical goods across owners share canonical identity but never stock; concurrent creation cannot duplicate codes or identities; readable SKU collisions are resolved deterministically; Type changes fail through direct edits and category reparenting; old aliases still resolve; 16-character codes fit every snapshot; partial purchase receipts/returns and conversions preserve exact source/target stock; INV inventory scans cannot resolve as invoices/invitations; migration is repeatable and reconciles pre/post stock and transaction totals.

This migration can substantially change the business identifier system without rewriting every relational foreign key. The existing canonical and owner boundaries are useful foundations; the largest required change is a complete variant-combination model and an explicit definition of what the client calls one Product.

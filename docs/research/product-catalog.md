# Admin Product Catalog: Correct Collection and Flow

**Scope.** This note traces the Admin **Product Catalog / All Products** page, the product-domain entities, and the existing create/view flows using repository sources only. It describes baseline commit `4de354df6910d7c2897b0165848d5bb6da508e69`; no web sources were used and no application code was changed.

## Conclusion

The Admin Product Catalog should list Admin-owned **Brand Products** (`product` rows), not every **Core Product Identity**. A Core Product Identity is only the shared root identity; one Brand Product is the owner-specific product for one core identity and one brand, with one or more Owner Variants ([`CONTEXT.md:29-47`](../../CONTEXT.md#L29)). The schema reinforces that split: `core_product_identity` is the canonical/master list ([`packages/db/src/schema/core-product.ts:31-42`](../../packages/db/src/schema/core-product.ts#L31)), while `product` carries the brand, price, status, visibility, scheduling, creator scope, and link back to the core identity ([`packages/db/src/schema/product.ts:59-83`](../../packages/db/src/schema/product.ts#L59), [`packages/db/src/schema/product.ts:164-193`](../../packages/db/src/schema/product.ts#L164)).

Therefore the intended empty state follows naturally: if there are no Admin-owned `product` rows, the Product Catalog is empty even when many Core Product Identities exist. The page should offer **Create Product**, and core/type/category selection should happen inside that creation flow. Draft and inactive products should remain visible in the management catalog; “actual product” and “currently consumer-sellable” are different states.

## Current mismatch

The sidebar already expresses the correct information architecture: **Product Catalog → All Products** points to `/dashboard/admin/products`, while **Core Identities** is a separate Setup page ([`apps/web/components/dashboard/admin-sidebar.tsx:57-83`](../../apps/web/components/dashboard/admin-sidebar.tsx#L57)). The All Products page nevertheless queries `adminCoreProduct.getAll` and renders `coreProducts` ([`apps/web/app/(dashboard)/dashboard/admin/products/page.tsx:220-227`](../../apps/web/app/(dashboard)/dashboard/admin/products/page.tsx#L220)). Its table labels each row as a Core Identity and gives View/Add-or-Edit-Configuration actions ([`apps/web/app/(dashboard)/dashboard/admin/products/page.tsx:373-430`](../../apps/web/app/(dashboard)/dashboard/admin/products/page.tsx#L373)); its header and statistics also explicitly describe/count core identities ([`apps/web/app/(dashboard)/dashboard/admin/products/page.tsx:455-468`](../../apps/web/app/(dashboard)/dashboard/admin/products/page.tsx#L455)).

That means the page can never be empty merely because no configured product exists: the empty state is driven by the Core Identity collection ([`apps/web/app/(dashboard)/dashboard/admin/products/page.tsx:562-575`](../../apps/web/app/(dashboard)/dashboard/admin/products/page.tsx#L562)). The row-click dialog compounds the boundary leak by starting from a core identity, then loading its derived configuration and choosing the first active configured product as the editable product ([`apps/web/app/(dashboard)/dashboard/admin/products/page.tsx:673-705`](../../apps/web/app/(dashboard)/dashboard/admin/products/page.tsx#L673)).

## Correct domain seam

The correct primary collection is the `product` table filtered to `creatorSource = "admin"`:

- A `product` row is one actual admin, warehouse, or shop product and has partial unique indexes enforcing one product per core+brand in the relevant owner scope ([`packages/db/src/schema/product.ts:197-217`](../../packages/db/src/schema/product.ts#L197)).
- Its selected variants/reference prices live in `product_variant_price` ([`packages/db/src/schema/product.ts:256-298`](../../packages/db/src/schema/product.ts#L256)). Concrete Owner Variants live in `product_variant` and point back to both the product and the canonical variant identity ([`packages/db/src/schema/product-variant.ts:68-101`](../../packages/db/src/schema/product-variant.ts#L68), [`packages/db/src/schema/product-variant.ts:212-258`](../../packages/db/src/schema/product-variant.ts#L212)).
- `catalog_variant` is not the row to show as a product. It is the platform identity for one exact core+brand+Variant Option combination shared across equivalent owner-local variants ([`CONTEXT.md:61-67`](../../CONTEXT.md#L61), [`packages/db/src/schema/catalog-variant.ts:18-43`](../../packages/db/src/schema/catalog-variant.ts#L18)).
- “Configuration” is derived from actual Admin-owned product rows; it is not a separate sellable entity. The configuration router states this explicitly and loads `product` rows by `coreProductId` plus `creatorSource = "admin"` ([`packages/api/src/routers/admin-product-config.ts:159-173`](../../packages/api/src/routers/admin-product-config.ts#L159), [`packages/api/src/routers/admin-product-config.ts:207-244`](../../packages/api/src/routers/admin-product-config.ts#L207)).

## Existing list and view support

No new data model or list endpoint is required. `product.getAdminWebViewProducts` already returns only Admin-owned products and includes category, subcategory, brand, images, Brand links, concrete variants, and variant prices ([`packages/api/src/routers/product.ts:571-621`](../../packages/api/src/routers/product.ts#L571)). With no Admin products, it returns `products: []`.

The Admin Web View already demonstrates a product-row projection suitable for reuse: it calls that endpoint, builds brand-scoped cards with variant prices, supports status/category/brand/variant filters, and has an Add Product action ([`apps/web/app/(dashboard)/dashboard/admin/web-view/page.tsx:204-267`](../../apps/web/app/(dashboard)/dashboard/admin/web-view/page.tsx#L204), [`apps/web/app/(dashboard)/dashboard/admin/web-view/page.tsx:306-380`](../../apps/web/app/(dashboard)/dashboard/admin/web-view/page.tsx#L306), [`apps/web/app/(dashboard)/dashboard/admin/web-view/page.tsx:464-560`](../../apps/web/app/(dashboard)/dashboard/admin/web-view/page.tsx#L464)). Its true-empty state already has the requested semantics: “No products yet,” explains that brand+variant products populate the listing, and links to `/dashboard/admin/products/new` ([`apps/web/app/(dashboard)/dashboard/admin/web-view/page.tsx:916-930`](../../apps/web/app/(dashboard)/dashboard/admin/web-view/page.tsx#L916)).

The existing detail flow is also product-based. Each card links with its `productId` (and optional brand scope) to `/dashboard/admin/web-view/[id]` ([`apps/web/app/(dashboard)/dashboard/admin/web-view/page.tsx:849-862`](../../apps/web/app/(dashboard)/dashboard/admin/web-view/page.tsx#L849)); that route fetches one Admin-owned product through `getAdminWebViewProductById` ([`apps/web/app/(dashboard)/dashboard/admin/web-view/[id]/page.tsx:14-35`](../../apps/web/app/(dashboard)/dashboard/admin/web-view/%5Bid%5D/page.tsx#L14), [`packages/api/src/routers/product.ts:623-674`](../../packages/api/src/routers/product.ts#L623)). The product edit route likewise loads by product ID and uses the product-specific editor for core-managed Admin products ([`apps/web/app/(dashboard)/dashboard/admin/products/[productId]/edit/page.tsx:9-29`](../../apps/web/app/(dashboard)/dashboard/admin/products/%5BproductId%5D/edit/page.tsx#L9), [`apps/web/app/(dashboard)/dashboard/admin/products/[productId]/edit/edit-product-client.tsx:11-24`](../../apps/web/app/(dashboard)/dashboard/admin/products/%5BproductId%5D/edit/edit-product-client.tsx#L11)).

## Existing creation flow

`/dashboard/admin/products/new` already supports creation with or without a preselected `coreProductId` ([`apps/web/app/(dashboard)/dashboard/admin/products/new/page.tsx:3-19`](../../apps/web/app/(dashboard)/dashboard/admin/products/new/page.tsx#L3)). Without a query parameter, `ProductForm` lets the admin select type/category/subcategory and an unconfigured Core Product Identity; it filters out cores that already have Admin configuration ([`apps/web/components/features/product/components/product-form.tsx:359-395`](../../apps/web/components/features/product/components/product-form.tsx#L359)).

The server creation contract enforces the requested shape: a Core Product Identity, at least one brand, and at least one variant per brand are mandatory ([`packages/api/src/routers/product.ts:676-739`](../../packages/api/src/routers/product.ts#L676)). Product existence—not a leftover template—is the source of truth for whether the core has been created ([`packages/api/src/routers/product.ts:768-782`](../../packages/api/src/routers/product.ts#L768)). The transaction creates one Admin `product` row per selected brand, links it to the core, and synchronizes its variant prices/concrete variants ([`packages/api/src/routers/product.ts:888-998`](../../packages/api/src/routers/product.ts#L888)).

## Recommended implementation boundary

1. Keep the page and navigation label **Product Catalog** / **All Products**.
2. Replace its `adminCoreProduct.getAll` collection with Admin-owned `product` rows from `product.getAdminWebViewProducts` (or extract a shared query/view-model from the existing Web View implementation).
3. Render one row/card per Brand Product with its brand, configured variants, status, visibility, and product-level View/Edit actions. Do not render unconfigured Core Product Identities as catalog rows.
4. Add a prominent **Create Product** action to `/dashboard/admin/products/new`; let the existing form own Core Identity, brand, and variant selection.
5. Use a true collection-empty state only when the Admin product query returns zero rows. A separate “no filter matches” state should not show the creation CTA as though the catalog were empty.
6. Keep inactive/draft products in the admin management list so they can be edited/reactivated. Apply consumer sellability rules only to public catalog projections: Admin ownership, active/public/published product, valid core+brand linkage, and an active configured canonical variant ([`packages/api/src/routers/helpers/reference-product-catalog.ts:58-85`](../../packages/api/src/routers/helpers/reference-product-catalog.ts#L58)).

## Test gap

The repository has unit coverage for public/canonical sellability, including invalid status, visibility, scheduling, and broken canonical variant linkage ([`packages/api/src/routers/helpers/reference-product-catalog.test.ts:61-193`](../../packages/api/src/routers/helpers/reference-product-catalog.test.ts#L61)). No direct test was found for the Admin Product Catalog page or `getAdminWebViewProducts`. The implementation should add at least a page/view-model test proving that zero Admin products renders the true empty state even when Core Product Identities exist, and that one configured brand product produces one catalog entry with its variants.

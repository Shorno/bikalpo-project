02

What was—and was not—counted

The boundary follows the functioning web product through frontend, API, authentication, database schema, environment contracts, and its server. It intentionally avoids native-app credit.

Included as web-product work

  • apps/web authored routes, components, hooks, libraries, schemas, types and utilities
  • packages/api/src, packages/auth/src, and authored packages/db/src
  • packages/env/src, relevant configuration, and apps/server/src
  • Current ownership from git blame; history from non-merge commits

Excluded or discounted

  • apps/native—excluded completely
  • Generated migrations/meta, build caches, lockfile, docs and static/binary assets
  • property-location-data.json—14,963 imported data lines that would artificially inflate Rayhan
  • Shared shadcn-style UI primitives remain in source totals but are not accepted as strict feature-survivor proof

Payment score = 60% current surviving code + 25% filtered historical churn + 15% web non-merge commits.

10

Limits you should disclose

A fair report is explicit about what its evidence cannot prove.

Git measures durable authorship, not human value

It cannot see planning, meetings, product decisions, manual QA, customer support, deployment work performed elsewhere, or code copied between accounts.

“Untouched” does not mean “never assisted”

Strict survivor files have no later Git author modifying them under the tested rule. That does not prove nobody reviewed, advised, paired, or fixed behavior outside those files.

Line counts have known biases

Formatting, generated code, datasets and scaffolded components can inflate totals. The largest obvious dataset and generated artifacts were excluded, and shared UI scaffolds were barred from survivor claims.

Runtime confidence is bounded

A successful production build is meaningful, but it is not end-to-end proof of every live workflow. Eight test files need the correct isolated environment before a fully green suite can be claimed.
